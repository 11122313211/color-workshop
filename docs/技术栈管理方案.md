> 版本：v1.0 ｜ 日期：2026-11-12 ｜ 状态：草案
> 配套文档：[PRD-色彩管理闭环AI产品.md](./PRD-色彩管理闭环AI产品.md)

## 2. 算法层（自研封装 + 成熟开源）

算法层是产品的核心底座，负责所有色彩科学计算。**三个开源库各司其职，由自研封装层统一编排**。

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **Little-CMS (lcms2)**，经 **Pillow ImageCms** 封装 | ICC profile 读写、CMM 转换、色彩空间互转（RGB/Gray/CMYK/Lab/XYZ）、色域映射、软打样、profile 检查 | 行业事实标准，被 Pillow、OCIO 等大量项目依赖，成熟度极高 | **直接用** |
| **colour-science (colour)** | CIEDE2000 色差计算、完整色度学算法体系、色彩外观模型（CIECAM02/16）、数据集 | 学术社区广泛使用，色度学算法权威来源，NumFOCUS 关联项目 | **直接用** |
| **coloraide** | 高层色彩空间互转、插值、色彩距离、色域映射高层封装、色彩混合 | 纯 Python、API 现代、活跃维护，文档完善 | **直接用** |

**三者分工逻辑**：
- **lcms2** 管 ICC/CMM（底层引擎）：负责 ICC profile 读写与实际跨设备转换，是行业标准，无可替代。
- **colour** 管色度学（科学算法）：负责 CIEDE2000 等色差计算与色度学算法，填补 lcms2 在色差计算上的空白。
- **coloraide** 管高层计算（产品接口层）：负责高层色彩运算，API 现代，适合作为产品算法层的统一调用接口。

**自研：产品级算法编排封装层**
- 将 lcms2、colour、coloraide 整合为统一、易用的产品接口与工作流编排。
- 这是**产品核心价值**所在，不是简单堆叠开源库，而是封装出"测量→转换→校正→验证"的闭环算法流水线。
- 负责渲染意图推荐、智能色域映射的调度、校正矩阵的组装等业务编排。

**备选/补充**：
- **OpenColorIO (OCIO)**：仅在产品明确面向影视 LUT 工作流时作为补充（支持 .cube/.3dl 等 LUT 格式、ACES 兼容）。ICC 支持依赖 lcms2。对通用色彩管理产品偏重，非首选。

## 3. AI 层（成熟开源 + 自研调优）

AI 层负责色卡识别、色差预测、校正生成等智能能力。**训练/推理框架与检测模型用成熟开源，模型业务化调优需自研。**

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **PyTorch** | 模型训练（色卡检测、色差回归、校正生成） | CV 生态最成熟，torchvision 提供预训练模型与权重，TorchServe 可部署 | **直接用** |
| **ONNX Runtime** | 跨平台推理（服务端 + 移动端/边缘） | 生产级推理引擎，跨平台覆盖完整（Linux/Win/macOS/iOS/Android/浏览器），端侧部署标准桥梁 | **直接用** |
| **YOLO（YOLOv8/v11 等）** | 色卡色块目标检测 | 生态成熟、实时性好，适合色卡检测，torchvision 提供现成检测模型 | **直接用** |

**自研：AI 模型业务化训练与调优**
- **数据标注**：色卡图像标注、实测色差配对数据采集与标注。
- **针对硬件的精度调优**：针对特定相机/色度计的模型精度调优。
- **混合架构模型设计**：采用"ICC 物理先验 + AI 补非线性"的混合架构，保留可解释结构，避免纯黑箱，兼顾精度与工程兼容性。这是调研的核心结论——传统数学方法（空间转换、色差公式）无需 AI 化，AI 价值集中在"非线性感知优化、复杂条件下的估计、端到端回归"三类任务。

**端侧推理可行性**：色卡识别任务模型规模小，通过 ONNX Runtime 可在移动端/边缘设备运行，适合配套硬件的本地采集场景。

## 4. 后端层（成熟开源）

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **FastAPI** | 后端 API 服务 | 基于 Starlette + Pydantic，原生 async/await，高性能，自动 OpenAPI/Swagger 文档，Pydantic 自动校验，与算法层同语言 | **直接用** |
| **Celery + Redis** | 批量色彩转换/校正的异步任务队列 | Python 最成熟的分布式任务队列，Redis 作为 broker 与结果后端，适合重计算任务的异步化与水平扩展 | **直接用** |

**说明**：
- FastAPI 的 BackgroundTasks 适合轻量后台任务；批量色彩转换、批量校正等重计算长任务用 Celery。
- 与 Python 色彩算法栈（Pillow/colour/coloraide）同语言，开发效率高，异步天然适合色彩转换等 I/O 与计算混合场景。

## 5. 前端层（成熟开源）

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **React（或 Vue）+ WebGL/Canvas** | 色卡展示、色彩预览、ΔE 可视化 | 生态成熟，WebGL 适合大规模色卡渲染与实时交互 | **直接用** |
| **D3.js + color.js / colorjs.io** | CIE 1931 色度图、色域覆盖图、前端色彩计算 | D3 内置色彩空间工具与几何原语，是科学可视化的标准工具；color.js 提供浏览器端色彩计算，与后端 coloraide 语义对齐 | **直接用** |
| **Tauri** | 跨平台桌面端（配套硬件的本地采集/预览客户端） | 利用系统原生 Web 渲染器，包体积远小于 Electron，复用前端代码，Rust 写后端逻辑，安全性高 | **直接用** |

**说明**：
- 桌面端优先选 **Tauri**（轻量、安全、复用前端代码）；若团队已深度使用 Electron 生态或有复杂 Node.js 依赖，可选 Electron，但包体积与内存占用更大。
- 前端色彩计算用 color.js，与后端 coloraide 语义对齐，便于前后端一致。

## 6. 数据层（成熟开源）

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **PostgreSQL** | 设备信息、ICC profile 元数据、色卡定义、测量数据、用户数据存储 | 关系型成熟稳定，支持复杂查询与关联，可扩展 PostGIS 用于色域几何存储 | **直接用** |
| **Redis** | 缓存（profile/色卡缓存）、Celery broker、实时测量数据 pub/sub | 高性能内存存储，Celery 标配 | **直接用** |
| **MinIO（私有化）/ S3（云）** | ICC profile 文件、原始图像、测量数据文件的对象存储 | 兼容 S3 协议，私有化部署首选 | **直接用** |

## 7. 部署层（成熟开源）

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **Docker + Docker Compose** | 私有化一键部署、开发环境 | 标准化容器化，私有化部署首选 | **直接用** |
| **Kubernetes** | SaaS 云原生编排、水平扩展 | 云原生部署标准，支持无状态服务与有状态层的独立扩展 | **直接用** |

**部署方案**：
- **SaaS**：Docker + Kubernetes，FastAPI 无状态服务水平扩展，Celery worker 独立扩展，PostgreSQL + Redis + MinIO 作为有状态层。模型推理服务（ONNX Runtime/TorchServe）独立部署。
- **私有化**：Docker Compose 一键部署全栈，适合企业内网，模型与数据本地化。

## 8. 硬件对接层（半自研）

硬件对接层是软硬件一体产品的关键环节，**底层通信库用成熟开源，设备协议适配需自研**。

| 技术 | 用途 | 成熟度 | 采用方式 |
|---|---|---|---|
| **pyserial** | 色度计/分光光度计串口（含 USB-CDC 虚拟串口）通信 | Python 串口扩展，跨平台（Win32/macOS/Linux/BSD），标准通信层 | **直接用** |
| **pyusb** | USB 设备直接通信（USB HID/自定义 USB 协议设备） | 基于 libusb 的 Python USB 通信库，跨平台 | **直接用** |

**自研：设备适配层**
- 各厂商（X-Rite、Datacolor、Konica Minolta、彩谱、远方等）设备的 USB 协议多为厂商私有，**无统一的 ICC 设备通信标准**。
- pyserial/pyusb 提供底层通信能力，但**每个设备型号的指令集和数据解析需针对厂商文档自研适配层**。
- 优先自研配套入门硬件，保证体验闭环；同时提供第三方硬件适配接口，兼容国内厂商测量设备，扩大生态。

## 10. 依赖与版本治理

### 10.1 版本锁定策略
- **算法层**：lcms2、colour-science、coloraide 锁定经过验证的稳定版本，避免核心算法行为变化影响精度与验收。
- **AI 层**：PyTorch 大版本升级需回归测试模型精度；ONNX Runtime 跟随模型格式要求升级。
- **后端/前端/数据/部署层**：遵循语义化版本，在 LTS/稳定版本上迭代，避免激进升级。

### 10.2 依赖更新节奏
- 建立依赖清单（含版本、许可证、用途），定期（季度）评估更新。
- 安全更新（CVE）优先处理；功能更新按迭代节奏评估，不盲目跟进最新版。

### 10.3 安全与合规（开源许可证）
- 建立许可证台账，区分许可类型（如 lcms2 的 MIT、colour-science 的 BSD-3-Clause、PyTorch 的 BSD 类、FastAPI 的 MIT、Tauri 的 MIT/Apache-2.0 等），避免 GPL 类传染性许可污染商业产品。
- 商业化前做一次全面的许可证合规审查。

### 10.4 技术债管理
- 自研封装层与适配层保持清晰的接口定义，避免与开源库耦合过深。
- 算法精度回归测试纳入 CI，防止重构或升级引入精度回退。
- 硬件适配层按设备型号隔离，新增设备不影响已有适配。

## 11. 技术演进路线（与产品版本对齐）

| 阶段 | 版本 | 技术研发重点 |
|---|---|---|
| **MVP** | V0.1 | 搭建算法底座（lcms2/colour/coloraide）与自研封装层；后端 FastAPI + Celery 基础架构；前端基础可视化（D3 色度图）；硬件对接层（pyserial/pyusb + 入门设备适配）；AI 色卡检测模型（YOLO + ONNX Runtime）初版 |
| **V1.x** | V1.0 | 完善 AI 混合架构模型（ICC 先验 + 神经网络）；智能校正/profile 生成模型；ΔE 预测与闭环迭代引擎；色域可视化增强；第三方硬件适配接口；多场景算法插件化雏形 |
| **V2.x** | V2.0 | 工业场景算法（纺织配色、产线在线检测）；AI 归因分析模型；批量任务编排与水平扩展（K8s）；企业级权限多租户；私有化部署方案成熟化 |
| **平台化** | V3.0 | 算法引擎可插拔；场景插件生态开放；色彩资产库；模型与数据资产沉淀；跨平台端侧推理优化 |

### 研发原则
- **物理先验优先**：以 ICC/色度学为骨架，AI 做增强层，不做纯黑箱替代，保证精度可验证、可被工业标准采纳。
- **混合架构**：AI 补非线性与感知优化，保留可解释结构。
- **封闭场景先行**：优先在封闭场景（固定设备、固定光源、固定流程）积累真实数据，再逐步扩展，避免一开始追求跨设备通用大模型。
- **硬件适配渐进**：优先自研配套硬件保证体验，第三方硬件按需适配，控制研发成本。

## 附：选型依据摘要

以下结论来自技术调研，支撑本方案选型：

1. **算法底座最佳组合**：lcms2（ICC/CMM）+ colour-science（色度学）+ coloraide（高层计算），三者各司其职，覆盖 ICC profile、CMM 转换、CIEDE2000 色差、高层色彩运算的全部需求。
2. **AI 标准组合**：PyTorch（训练）+ ONNX Runtime（推理）+ YOLO（色卡检测），端侧推理通过 ONNX Runtime 导出即可，无需重写。
3. **后端前端数据部署均有成熟方案**：FastAPI、Celery+Redis、React+D3、PostgreSQL+Redis+MinIO、Docker/K8s，无需从零构建。
4. **需自研三处**：硬件设备协议适配、产品级算法编排封装、AI 模型业务化调优——这恰是产品的差异化竞争力所在。
